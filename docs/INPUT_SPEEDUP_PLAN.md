# План: ускорение ввода параметров на площадках

Цель — сократить время заполнения формы (видно по live-окнам: клики, выбор дат, ввод
текста идут медленно). Источник медленности — НЕ сеть, а как провайдер драйвит форму:
фиксированные паузы «на всякий случай», посимвольный ввод и последовательное
заполнение. Ниже — план глубокого анализа и оптимизации **без потери надёжности**
(URL-сверка и проверка формы уже ловят «слетевшие» значения — это страховка).

## Фаза 0. Замер базовой линии (без этого не оптимизируем)
1. `scripts/profile_input.py`: контекст-менеджер/декоратор, логирующий длительность
   каждого шага провайдера (`_select_departure_city`, `_select_country`, `_select_dates`,
   `_set_nights`/`_select_nights`, `_select_tourists`, `_select_operators`, `_select_stars`,
   `_select_meal`, клик «Найти»).
2. Прогнать ≥5 раз на каждом сайте (Москва→Турция, типовой набор), собрать **медианы**.
3. Таблица «шаг → медиана, мс» по обоим сайтам → найти топ-3 самых долгих шага.
   Оптимизируем только их (правило: не угадывать).

## Фаза 1. Карта реальных задержек (что чинить)
Три источника, по убыванию подозрения:

1. **Фиксированные `page.wait_for_timeout(300…900)` после каждого действия.**
   Их в провайдерах десятки. Каждая — слепое ожидание. Заменить на **событийные**
   ожидания: `wait_for_selector(state=...)`, `wait_for_function(...)`, `locator.wait_for()`,
   ожидание изменения значения в DOM. Ждём ровно до готовности, а не «с запасом».
2. **Посимвольный ввод `page.type(..., delay=40)`** (город/страна/оператор).
   40 мс/символ × длинные строки. Варианты: снизить `delay` до 15–20; где автодополнение
   не требует посимвольного триггера — `fill()`/`insert_text`; проверить, что подсказки
   всё равно появляются.
3. **Пампинг live-кадров** (`start_frame_pump`: скриншот каждые 1400 мс, jpeg q=62).
   Конкурирует за CDP-канал и CPU во время кликов → визуально «тормозит». Оценить:
   увеличить интервал во время заполнения формы либо снизить качество/паузить пампинг
   на критичных шагах.

## Фаза 2. По каждому контролу — чего РЕАЛЬНО надо дождаться
Вместо паузы — конкретный сигнал готовности (снять анализом DOM/XHR, см. Фаза 4):
- **Город/страна (Sletat, ввод текстом):** дождаться появления списка подсказок
  (`.city-selector-list …` / `.slsf-country-to__select-text`), кликнуть, дождаться, что
  инпут принял значение — вместо `wait_for_timeout(800..900)`.
- **Город/страна (Tourvisor):** список лениво подгружается — уже скроллим в JS; заменить
  фикс-паузы на ожидание появления искомой строки.
- **Даты:** ждать рендер календаря уже умеем (`button.rdrDay` / `.TVCalendarTitleControlMonth`);
  убрать лишние паузы между кликами заезд/выезд.
- **Ночи (Sletat, виртуализованный список):** в JS-скролле заменить `sleep(45)` на
  ожидание появления нужного `li` (MutationObserver/polling по наличию).
- **Туристы (счётчик +/-):** между кликами `wait_for_timeout(150..200)` → ожидание
  изменения числа в `.adult-counter-label` / `.TVTouristCount`.
- **Операторы:** панель виртуализована и пересортировывается — здесь осторожно, мерить
  отдельно (возможно, основной вклад в медленность).

## Фаза 3. Параллелизация независимых полей (осторожно, после замеров)
Часть полей можно заполнять без переоткрытия общих панелей. Реактивные формы
чувствительны к порядку, поэтому: только то, что доказано безопасно прогоном
(URL-сверка/form-verify зелёные). Высокий риск — низкий приоритет.

## Фаза 4. Анализ самих сайтов (чтобы ждать событие, а не таймер)
- Через CDP/`page.on('requestfinished')`/`page.on('response')` снять, какие XHR и
  перерисовки реально происходят после каждого действия → определить точный «сигнал
  готовности» каждого контрола.
- Расширить `scripts/analyze_sletat_full.py` / `inventory_tourvisor.py` замером
  «время до готовности контрола» и фиксацией селектора-сигнала.

## Фаза 5. Защита от регрессий
- Каждое сокращение паузы — отдельным шагом + прогон (form-verify + URL-сверка ловят
  «слетело»). Падает проверка → откат конкретного шага.
- e2e-тест «бюджет времени ввода»: заполнение формы укладывается в целевой X c
  (регрессия на скорость, а не только на корректность).
- `scripts/profile_input.py` печатает «до/после» по шагам — оптимизация измерима.

## Быстрые победы (низкий риск, можно сразу после Фазы 0)
- `delay=40` → 15–20 в `page.type`.
- Очевидно лишние `wait_for_timeout(800)` после выбора из списка → `wait_for_selector`
  готовности следующего контрола.
- Снизить частоту/качество frame-pump на время заполнения формы.

## Метрики успеха
Зафиксировать текущее медианное время ввода на каждом сайте и цель −40…60 %, не ухудшая
прохождение form-verify/URL-сверки на наборе из Фазы 0.
