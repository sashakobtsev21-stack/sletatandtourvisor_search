# Как добавить новый live-тест в testkit/catalog.py

Live-тесты — это сценарии, которые **реально открывают сайт площадки в Playwright**
и проверяют что-то на живой выдаче. В отличие от unit-тестов (быстрые pytest без
браузера), live-тесты:

* запускаются только из вкладки «Автотесты» в дашборде ИЛИ `pytest -m e2e`;
* требуют интернет и работающий сайт-провайдер;
* стоят 60–120с каждый (поэтому опт-in);
* регистрируются в `REGISTRY` через `add(group, name, fn)` при импорте `catalog.py`.

## 1. Куда положить

`src/toursearch/testkit/catalog.py` — единый файл-каталог (намеренно не сплитнут, см.
обсуждение в audit-логах). Найдите секцию по тематике:

* `# ============ Live UI: <тематика> ============` — UI-проверки формы/выдачи;
* `# ============ Live: Сценарий — <тематика> ============` — сценарные проверки.

Добавляйте новые тесты в конец соответствующей секции.

## 2. Шаблон самой простой live-проверки

```python
G = "Live: Сценарий — моя новая группа"
_GROUP_DESC[G] = "Что эта группа проверяет в одну строку."

async def my_test():
    """Описание что именно проверяет."""
    # 1. Получить страницу с актуальной сессией результатов
    page = await _results_page()           # один прогон на всю Sletat-сессию
    # 2. Что-то проверить
    title = await page.locator(".some-selector").inner_text()
    _assert("expected" in title, f"в заголовке нет 'expected': {title!r}")

add(G, "моя новая проверка", my_test)
```

## 3. Использование Sessions (важно для скорости)

`_results_page()` / `_results_hotels_page()` — кешированные сессии Playwright:
**один прогон поиска на ВСЕ тесты в категории**. Не пишите `async with async_playwright()`
вручную — это поднимет новый браузер на каждый тест.

## 4. Категория группы

`_category(group)` определяет порядок и поведение:

| Префикс | Категория | Когда запускается |
|---|---|---|
| `"Health-..."` | `healthcheck` | первым; проверяет что форма не сломана |
| (без `Live:`) | `fast` | unit-level быстрые проверки |
| `"Live: смоук..."` | `smoke` | первый live-блок |
| `"Live: Сценарий — направлен..."` | `coverage` | покрытие направлений |
| `"Live: Сценарий — отели"` | `hotels` | режим отелей |
| `"Live: Сценарий — персон..."` | `e2e` | персоны, срез |
| `"Live: Сценарий — ..."` | `positive` | звёзды/цена/оператор/питание |
| `"Live: ..." (прочее)` | `ui` | UI-проверки |
| `"Live: границ... / негатив..."` | `negative` | граничные/негативные |

Категория влияет на порядок прогона в `_CAT_ORDER`.

## 5. Проверка перед коммитом

```bash
# 1. catalog.py всё ещё импортируется (REGISTRY.add не падает)
pytest -q tests/test_catalog.py

# 2. сам тест запускается живьём (с интернетом)
pytest -m e2e -k "моя новая проверка" -v

# 3. ничего не сломалось
pytest -q
```

## 6. Когда НЕ нужен live-тест

* проверка чистой логики парсинга/маппинга → unit-тест в `tests/test_<provider>.py`
* проверка формата URL поиска → `tests/test_urlcheck.py`
* проверка `_OPERATOR_MAP`/`MEAL_BTN` → быстрый unit в `tests/test_catalog.py`

Live-тест нужен ТОЛЬКО когда без живого Playwright проверка не имеет смысла:
«реально ли сайт сейчас отдаёт цены в RUB», «реально ли работает фильтр по звёздам».

## 7. Образцы в коде

Откройте `testkit/catalog.py` и найдите готовые группы:

* `"Live: Сценарий — звёзды и рейтинг"` — простая позитивная проверка фильтра
* `"Live: Сценарий — отели — мин. цена и звёзды"` — режим отелей с агрегатом
* `"Live: смоук — sletat"` — минимальный набор «дошло до выдачи»
