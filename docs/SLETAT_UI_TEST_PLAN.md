# План live UI-тестов формы поиска Sletat

Цель — покрыть **весь функционал поиска Sletat** фокусными live-тестами интерфейса:
каждый тест проверяет поведение, логику и валидацию ОДНОГО элемента (или одного
взаимодействия), а не «прогон поиска целиком». Это заменяет текущую live-группу
«Live: Sletat (реальные сценарии)» (50 end-to-end прогонов) в разделе **Автотесты**.
Health-check-группа остаётся как есть.

Селекторы — из `SITES.md` (выверены живой инспекцией). Принцип: `data-testid`/`id`-префикс
→ BEM (`uis-*`,`slsf-*`,`blinchik__*`) → структура; хешированные CSS-in-JS не использовать.

---

## 0. Принципы тест-дизайна (как делает опытный тестировщик)

**Что значит «фокусный UI-тест»:** проверяем взаимодействие с элементом и его контракт —
рендер/наличие → дефолтное состояние → корректный ввод/выбор → невалидный ввод → влияние
на зависимые элементы → отражение в состоянии формы/URL. Не дублируем сквозной поиск.

**Категории проверок (применяются к каждому элементу):**
1. **Presence/Render** — элемент и его якоря на месте (это и есть расширенный health-check).
2. **Default** — значение по умолчанию («Все курорты», «Любая», «Без стопов» вкл.).
3. **Happy-path** — корректный ввод/выбор приводит к ожидаемому состоянию.
4. **Validation/Negative** — границы и запреты (окно дат ≤13, ночи от≤до, цена от≤до, мин. 1 взрослый, прошедшие даты).
5. **Dependency** — влияние на другие элементы (страна→курорты, ночи от→до, Туры↔Отели).
6. **Persistence** — выбранное реально применяется (отражено в поле/URL/выдаче; ловит классику «виджет показал одно, ушло другое»).

**Архитектура исполнения (критично для live):** открытие формы ~4–5 c, поэтому НЕ открываем
браузер на каждый тест. Тесты сгруппированы по **сессиям** с общей страницей и сбросом
состояния между кейсами:
- Сессия **FORM-TOURS** — форма «Туры» (группы 1–18, 23, 24): открыть форму один раз,
  между кейсами — «Сбросить фильтры»/перезагрузка.
- Сессия **FORM-HOTELS** — вкладка «Отели» (группа 19).
- Сессия **RESULTS-TOURS** — один реальный прогон → проверки выдачи и блинчика (группы 20, 21).
- Сессия **RESULTS-HOTELS** — один прогон в режиме «Отели» (группа 22).
Итого ~4 открытия браузера + 1–2 доп. прогона ⇒ суммарно ~5–8 мин на все ~120 тестов.

**Анти-флаки:** только событийные ожидания (`wait_for_selector`/`wait_for_function`), без
фиксированных пауз; ретрай кейса до 2 раз; скриншот при падении; устойчивые селекторы;
для виртуализованных списков (ночи) — ожидание появления пункта, не пауза.

**Интеграция в `/tests`:** каждая группа ниже = группа реестра `testkit`, имя начинается с
«Live: …» → категория `live`. У каждого кейса — `description` «для чайников» и `live=True`.

## Приоритеты и порядок внедрения
1. **Smoke (~28 ⭐)** — сначала: ловят «форма сломана/редизайн» за ~2–3 мин. Это эволюция текущего health-check.
2. **Полный набор (~120)** — по сессиям FORM-TOURS → FORM-HOTELS → RESULTS-TOURS → RESULTS-HOTELS.
3. Миграция: убрать группу «Live: Sletat (реальные сценарии)» (50 сквозных), оставить health-check; новые группы 1–24 в категории `live`.

## Что нужно от инфраструктуры `testkit`
- Лёгкое расширение реестра: общая `LiveSession` (одна страница на сессию) + сброс между кейсами,
  чтобы не открывать браузер на каждый из ~120 тестов.
- Ретрай live-кейса (1–2 попытки) и скриншот при падении (уже есть в провайдере — переиспользовать).
- Все селекторы — из `SITES.md`; при расхождении тест падает с понятным «элемент X не найден» (= сигнал редизайна).

## Критерии готовности
- Все smoke зелёные на живом Sletat; полный набор зелёный (допускается карантинный список заведомо
  хрупких, напр. пагинация при малой выдаче).
- Среднее время полного прогона ≤ ~8 мин (за счёт сессий).
- Каждый кейс имеет понятное `description` в панели `/tests`.
