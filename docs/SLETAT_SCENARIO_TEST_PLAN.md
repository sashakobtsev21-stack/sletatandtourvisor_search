# План сценарных тестов Sletat: «параметры → поиск → сверка результатов»

Цель — добавить класс тестов, которого сейчас **почти нет**: задать параметры, запустить
реальный поиск и проверить, что **выдача честно соответствует фильтрам** (а не только что
сайт «принял» запрос). Это покрывает реальные пользовательские сценарии: любое направление,
любой состав тура, любые звёзды, курорты, питание, оператор, цена, режим.

Документ отвечает на вопрос пользователя: *сколько ещё тестов нужно для 100% сценариев и
будут ли тесты, которые сверяют результаты с параметрами*.

---

## 1. Что уже покрыто и чего НЕ хватает (честный аудит)

Текущий live-набор (25 групп / 89 кейсов) делится на:

| Что проверяет | Группы | Тестов | Класс |
|---|---|---|---|
| Элемент формы present/default/выбор/взаимодействие | GUI1–GUI24 | 81 | UI-контракт |
| Форма площадки жива (якоря) | Health-check | 2 | smoke |
| Сквозной прогон: `success` + **URL = параметры** | «Срез сценариев» | 8 | persistence по URL |

**Ключевой вывод (это и есть пробел, на который указывает пользователь):**

> Сверка по URL (`verify_sletat_search_url`) доказывает, что мы **задали сайту правильный
> вопрос**. Она НЕ доказывает, что **ответ (карточки/операторы) соответствует фильтрам.**

Пример незакрытого риска: выбрали 5★ + питание AI + цена ≤120k + оператор Anex — URL может
быть корректным, а в выдаче окажутся 3★, BB, 200k и оператор Pegas (фильтр на сайте «не
доехал», сортировка сбилась, парсер цены соврал). Сейчас такой баг **не ловится ни одним
тестом**. Именно сюда идёт весь новый набор.

**Новый класс тестов — «result-honoring» (сверка выдачи с параметрами):**
запустить поиск → распарсить выдачу/блинчик → утверждать, что КАЖДЫЙ результат удовлетворяет
каждому активному фильтру (или, где фильтр не виден в карточке, — что набор результатов
изменился ожидаемо).

---

## 2. Что реально проверяемо в выдаче (матрица верифицируемости)

Из карточки Sletat (`.search-result__list-item`) провайдер уже достаёт: **имя, звёзды
(`_stars-N`), рейтинг, направление (destination), цену, число операторов**; из блинчика —
**операторы + цены**. Отсюда — сила проверки по каждому параметру:

| Параметр | Видно в выдаче? | Сила сверки | Как проверяем |
|---|---|---|---|
| Страна / направление | да (destination) | 🟢 сильная | каждый отель ∈ стране/её курортам |
| Курорт (resort) | да (destination) | 🟢 сильная | destination содержит выбранный курорт |
| Звёзды | да (`_stars-N`) | 🟢 сильная | `stars ∈ выбранных` для всех карточек |
| Рейтинг (мин.) | да | 🟢 сильная | `rating ≥ порога` для всех |
| Цена (диапазон) | да | 🟢 сильная | все цены ∈ [min,max] |
| Оператор | да (блинчик) | 🟢 сильная | в блинчике/мин. цене — только выбранные |
| Сортировка | да (порядок) | 🟢 сильная | цены упорядочены |
| Валюта | да (символ/число) | 🟢 сильная | цены в выбранной валюте |
| Ночи | частично (на карточке тура) | 🟡 средняя | если показаны — в диапазоне; иначе URL + differential |
| Питание (board) | иногда (бейдж) | 🟡 средняя | где есть бейдж — совпадает; иначе differential (набор сузился) |
| Состав (взр/дети) | нет на карточке | 🟡 средняя | сверка по URL (kids/adults) + наличие выдачи |
| Чартер/прямые/трансфер/моментальное | нет (детали тура) | 🟠 слабая | differential: применение меняет/сужает выдачу + URL-флаги |
| Пляжная линия / тип отеля | нет на карточке | 🟠 слабая | differential (набор изменился) |

🟢 — утверждаем по каждому результату (самые ценные тесты).
🟡 — где атрибут виден, утверждаем по результату; иначе URL/differential.
🟠 — differential («фильтр действительно повлиял на выдачу») + сверка флага в URL.

> Вывод для инфраструктуры: для 🟢-параметров достаточно текущего парсера. Для 🟡 «ночи/
> питание» желателен **расширенный парсер карточки тура** (ночи, бейдж питания). Для 🟠
> верификация — через **differential** (сравнение размера/состава выдачи без фильтра и с ним),
> т.к. атрибут не вынесен на поверхность карточки.

## 3. Сколько всего сценариев? (комбинаторика и почему «100% буквально» невозможно)

Пространство параметров (классы эквивалентности из `models.py` + `refdata.py`):

```
города вылета 41 × страны 55 × ночи(классы) 6 × взрослые 8 × дети(классы) 6 ×
режим 2 × звёзды(классы) 8 × питание 6 × рейтинг 4 × пляж 4 × операторы(классы) ~15 ×
цена(классы) 5 × курорты(на страну) × флаги рейсов 2^5 × валюта 3 × сортировка 2 …
```

Полный декартов перебор ≈ **10¹²–10¹⁴ комбинаций** — физически неисполним: один реальный
поиск Sletat ≈ **6–15 c**. Даже 250 тестов — это уже ~30–40 мин прогона (при параллелизме
в 3–4 браузера — ~10–12 мин).

«100% сценариев» достигается не перебором, а как у опытного QA — **многослойным покрытием**:

1. **Each-choice (1-wise)** — каждое значение каждого параметра встречается хотя бы в одном
   исполненном поиске и проверено в выдаче. Это «дно», гарантирующее «каждая звёздность /
   каждый курорт / каждое направление покрыты».
2. **Pairwise (all-pairs, 2-wise)** — каждая ПАРА значений разных параметров встречается
   вместе хотя бы раз (ловит баги взаимодействия фильтров). Десятки тестов вместо триллионов.
3. **Boundary + negative** — границы (окно 13 дней, 1/мин/макс ночи, мин. 1 взрослый) и
   заведомо пустые выдачи (без зависания).
4. **Risk-based «персоны»** — курируемые реальные бронирования (самые частые сценарии).

Это и есть «эффективные 100%»: каждое значение проверено, все важные пары проверены,
границы и реальные журналы — отдельно.

## 5. Рекомендуемые уровни (что брать)

Пользователь просил **максимум** — целимся в **Full ≈ 250**, но строим фазами с ранней
пользой:

- **Core ≈ 110** (первая фаза, самое ценное):
  S1–S9 (56) + 14 популярных направлений из S10 + ужатый S12 (10) + S15 (14) +
  8 «персон» + базовый срез «Отели» (8). Даёт: **каждое значение фильтра сверено в выдаче ×1**,
  все популярные направления, границы, реальные журналы. Прогон ~6–8 мин (с параллелизмом).
- **Full ≈ 250** (цель): добавляет все 55 стран, 12 городов, pairwise (60), полный «Отели»
  (22), все 18 персон. Прогон ~10–14 мин при 3–4 параллельных браузерах.
- **Extended ≈ 320** (если нужно «совсем всё»): все 41 город (S11 +29) + направления в обоих
  режимах + расширенный pairwise. Прогон ~18–22 мин.
- **Exhaustive (декартов перебор)** — **НЕ делаем**: 10¹²⁺ комбинаций, неисполнимо; «100%»
  обеспечивают слои each-choice + pairwise + границы + персоны (см. §3).

## 6. Что нужно от инфраструктуры (testkit/провайдер)

1. **Result-introspection слой** (поверх существующего `_parse_hotels`/`_parse_blinchik`):
   - `extract_hotels(page) -> [{name,stars,rating,price,destination}]` — есть.
   - `extract_operators(page) -> [{name,price}]` — есть (блинчик).
   - **NEW** `extract_tour_cards(page) -> [{nights?, board?, operators_count}]` — для 🟡 ночи/питание.
   - `assert_results_honor(params, hotels, ops)` — единый матчер «выдача ∈ параметрам» по §2.
2. **ScenarioSession** — по аналогии с `LiveSession`: один поиск на сценарий, но между разными
   наборами параметров поиск **переисполняется** (фильтр нельзя надёжно «снять» на лету).
   Можно переиспользовать страницу для производных проверок (сортировка/пагинация того же
   набора).
3. **Параллелизм**: пул из 3–4 браузер-контекстов (или прогон через `Workflow`/несколько
   `LiveSession`) — иначе 250 × ~9 c последовательно = ~37 мин.
4. **Differential-хелпер**: `count_results(page)` до/после применения 🟠-фильтра.
5. **Анти-флаки**: событийные ожидания, ретрай кейса ≤2, скриншот при падении (переиспользуем
   из провайдера); «туров нет» — это валидный исход, не падение.
6. **Интеграция в `/tests`**: новые группы `live`, имя «Live: Сценарий — …», у каждого кейса
   человекочитаемый `description`. Старый «Срез сценариев» (8) поглощается S10/S16 и ретайрится.

## 7. Порядок внедрения (фазы)

1. **Фаза 0 — инфраструктура**: `assert_results_honor`, `extract_tour_cards`, ScenarioSession,
   differential-хелпер, параллельный прогон. + 2 образцовые группы (S1 звёзды, S5 оператор).
2. **Фаза 1 — Core (~110)**: S1–S9, популярные направления, границы, персоны, базовый «Отели».
3. **Фаза 2 — Full (~250)**: все страны/города, pairwise, полный «Отели», все персоны.
4. **Фаза 3 — Extended (опц.)**: все 41 город, оба режима для направлений.

## 8. Критерии готовности

- Каждое значение каждого фильтра проверено в **выдаче** (не только в URL) ≥1 раз.
- Все популярные направления зелёные; редкие — «успех ИЛИ корректное туров-нет».
- Pairwise-массив покрывает все пары основных фильтров.
- Полный прогон ≤ ~15 мин (за счёт параллелизма), допускается карантин заведомо хрупких.
- У каждого кейса — понятное `description` в `/tests`.
